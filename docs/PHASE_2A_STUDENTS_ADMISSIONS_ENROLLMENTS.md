# Phase 2A — Students, Admissions and Enrollments

## Included modules
- **Students:** branch-linked student profiles, guardian and emergency-contact details, lifecycle status, generated student numbers (`TBK-YYYY-000001`).
- **Admissions:** applicant profile, selected branch/course/intake, generated application number (`APP-YYYY-000001`), review status, reviewer and review timestamp.
- **Enrollments:** student/course/branch/cohort relationship, start and expected end dates, tuition and other fees, status, generated enrollment number (`ENR-YYYY-000001`).

## Admission workflow
1. Create an application against an active course and a branch the operator can manage.
2. Move it to Under review, Accepted, Rejected or Withdrawn.
3. An Accepted application can be converted once. Conversion creates the official Student record and a Pending Enrollment using the course's current fee values.
4. The application stores a protected link to the converted student. Repeated conversion is rejected.

## API endpoints
All endpoints require JWT authentication and return branch-scoped records.

- `GET/POST /api/students/`
- `GET/PATCH /api/students/{id}/`
- `GET/POST /api/admissions/`
- `POST /api/admissions/{id}/review/` with `status` and optional `review_notes`
- `POST /api/admissions/{id}/convert/`
- `GET/POST /api/enrollments/`
- `GET/PATCH /api/enrollments/{id}/`

List endpoints support `search` and `status` query parameters. Permanent deletion is disabled; records are retained and their status should be changed instead.

## Access rules
- System administrators can access all branches.
- Branch Managers and Admissions Officers can create/update student, admission and enrollment records in their assigned branches.
- Finance Officers, Instructors and Read-only Staff can read records in assigned branches.
- A user's records are not exposed across branches without an active branch membership.
- Every create, update, review and conversion action is written to the audit log.

## Data integrity
- Student, application and enrollment numbers are generated by the server and are unique.
- An enrollment's branch must match the student's registered branch.
- A student cannot have duplicate enrollments for the same course and cohort.
- Course selection for a new application or enrollment must reference an active course.
- Branches and courses are protected from deletion where linked records exist.

## Notes
Phase 2A is the administrative foundation. Finance transactions, attendance, academic history and student self-service workflows remain separate follow-on modules. Offline outbox envelopes are not automatically applied to these official records yet; do not use the foundation demo draft for live student data.

## Offline handling
The staff console can queue new Student, Admission and Enrollment records in IndexedDB while offline. The latest successful staff workspace snapshot supplies branch, course and existing-student selections. On reconnection, the authenticated server validates and creates the official records, assigns their permanent reference numbers and audits the result. Offline operations are create-only; edits, admission decisions and conversion remain online-only in this phase. Rejected records are retained in a local attention queue.
