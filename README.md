# TechBoK Web App — Phase 2A

A modular TechBoK-only institute management application.

## Stack
- Django 5 + Django REST Framework + Simple JWT
- Vue 3 + Vite (staff console :5173, student portal :5174)
- SQLite by default; PostgreSQL when `DATABASE_URL` is configured

## Included in this starter
- Custom user model with case-insensitive usernames
- Branches and per-branch role assignments
- Dynamic course catalogue (not hard-coded)
- JWT login/refresh endpoints
- Branch-aware API queryset filtering
- Audit event model and audit logging for API create/update/delete actions
- Student, admissions and enrollment records with branch-scoped APIs, approval/conversion workflow and audit events
- Starter staff and student Vue interfaces
- Database, permissions and API design documents

## Local setup

### Backend (Python 3.11+ recommended)
```bash
cd backend
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env   # Windows; on macOS/Linux use: cp .env.example .env
python manage.py makemigrations accounts branches courses audit offline_sync assessments students
python manage.py migrate
python manage.py createsuperuser
python manage.py seed_branches
# Optional module tests after migrations:
python manage.py test apps.students apps.offline_sync
python manage.py runserver 8000
```

The first superuser can create branches and assign branch memberships through Django admin. For an existing installation, keep your current `backend/.env` and `backend/db.sqlite3` files when copying this update over the project; apply the new migrations to the existing database. API docs for the starter endpoints are in `docs/API_SPECIFICATION.md`.

### Staff console
```bash
cd staff-console
npm install
npm run dev
```

### Student portal
```bash
cd student-portal
npm install
npm run dev
```

## Important production notes
This is a development starter, not a production-ready finance system. Before production: set a strong `DJANGO_SECRET_KEY`, configure `ALLOWED_HOSTS`, HTTPS, secure JWT storage/refresh strategy, persistent media storage, backups, monitoring, rate limiting, automated tests, and PostgreSQL. Do not use Django's development server in production. Audit logs are application-level records; production should additionally restrict database-level update/delete privileges and export security events to protected storage.


## Foundation upgrade: offline + assessments
See `docs/OFFLINE_AND_SYNC.md` for the added PWA shell caching, IndexedDB operation outbox, sticky headers, idempotent sync-envelope endpoint, and initial assessment schema. The sync endpoint is foundation-only: operation envelopes are acknowledged and recorded, but not yet applied to official module tables. Do not use the demo offline draft for live records.


## Phase 2A — Student lifecycle
The staff console now includes Student Directory, Admissions and Enrollments workspaces. Admission review and conversion create the linked student and pending enrollment. Reference numbers are generated by the backend. Records are branch-scoped, audited and retained (no permanent delete). New student, admission and enrollment records can be captured offline and synchronised when the same staff account reconnects. Offline edits, admission decisions and conversions remain online-only in this phase; see `docs/PHASE_2A_STUDENTS_ADMISSIONS_ENROLLMENTS.md` and `docs/OFFLINE_AND_SYNC.md`.
